## FlashBeat Web Studio (`web/`)

Standalone web app for the festival build. It is **not** part of the Unity project and
the Unity project is never moved.

### Stack (locked)

Void (native routes + pages) · Vite+ (`vp`) · React 19 + TypeScript · Panda CSS
(`@pandacss/dev` + `@pandacss/vite`) · Park UI (`@ark-ui/react` + `@park-ui/cli`) ·
lucide-react · react-konva (chart grid) · Ajv (contract validation).
**Never install Tailwind, shadcn/ui or a second UI system.**

### Commands

```sh
vp install          # install dependencies (also runs `void prepare` + `panda codegen`)
vp dev              # dev server on http://localhost:5173
vp check            # format + lint (oxfmt / oxlint)
npx tsc --noEmit    # type check (TypeScript 7)
npm test            # node --test tests/ (read API) && vitest run (src/lib/**)
vp build            # production build
panda codegen       # regenerate styled-system after a panda.config.ts change
```

`styled-system/` is generated and gitignored. `postinstall` regenerates it, so a fresh
clone only needs `vp install`.

The unit tests run with `vitest.config.ts`, not with `vite.config.ts`: the Void plugin
starts a workerd inspector that cannot run inside the Vitest worker. The read API
integration test runs with `node --test tests/`, because it starts the real Void dev
server against the local D1.

### Database (D1)

The three festival tables live in `db/schema.ts` and are generated into
`db/migrations/` with Void's built-in Drizzle/D1 support:

| Table            | Purpose                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `songs`          | Published song metadata plus the currently published chart version. `archived`/`archivedAt` hold the soft delete (issue #151). |
| `chart_versions` | Immutable chart snapshot per `(songId, version)`.                                                                              |
| `scores`         | Public score submissions.                                                                                                      |

```sh
void db generate     # regenerate db/migrations/ after a schema change
void db migrate      # apply pending migrations to the local D1
void db seed         # reset local D1, re-apply migrations, run db/seed.ts
void db status       # applied/pending migrations (local + deployment target)
node --test tests/  # read API integration tests (see "Read API")
```

The Cloudflare binding points at the single FlashBeat database
(`7de6fd23-dd7b-4e21-bddd-b28b33ee0462`) with `migrations_dir: "./db/migrations"`,
so `void db migrate --remote` and `cf d1 migrations apply` read the same SQL files
and share the `d1_migrations` bookkeeping table. Never reset the remote database:
ship a follow-up migration instead.

`db/fixtures/who.chart.json` is a byte-identical copy of the notes of
`Assets/Game/Resources/Who.json` (the `lyrics` block is not seeded)
and `db/fixtures/who.song.json` carries the matching metadata from
`Assets/Game/Scripts/Songs/GManager.cs`. The seed stores the chart file text
verbatim, so the published chart is identical to the one the Unity player ships.

### Chart editor (`/chart`)

The editor opens the legacy FlashBeat chart format
(`name`, `maxBlock`, `BPM`, `offset`, `notes[{type,num,block,LPB}]`, `lyrics`) and
writes it back unchanged.

- `src/lib/chart/` is pure logic: `import.ts` (read + validate), `export.ts` (write),
  `notes.ts` (edit operations), `timing.ts` (`60 / BPM * num / LPB`), `schema.ts`
  (Ajv against the frozen contract), `issues.ts` (warning severity of an issue),
  `youtube.ts` (video id parsing).
- **Lenient read (issue #208).** `import.ts` reads a chart in the lenient mode
  (`importChartLenient`): a chart whose _relations_ are broken is loaded and its
  violations come back as warnings, so a chart that was published before the
  semantic rules were unified can be repaired instead of being dropped with
  "Published chart failed validation". The song session
  (`src/lib/song-session/load.ts`) and the file import of the editor use it, and
  the warnings reach the operator through the validation panel. The publish API
  (`routes/api/v1/_publish-model.ts`) stays strict, and so do the validator tests.
- `src/lib/chart/chart.v1.schema.json` and `src/lib/chart/fixtures/sample-chart.json`
  are byte copies of `contracts/schemas/chart.v1.schema.json` and
  `Assets/Game/Resources/チュートリアル.json`. `.prettierignore` keeps the formatter
  away from them and `src/lib/chart/__tests__/contract-schema.test.ts` fails when they
  drift apart.
- The grid is `react-konva`. Konva needs a canvas, so the grid is loaded lazily and the
  route is not server rendered (`ssr = false` in `pages/chart.server.ts`).
- The preview is the YouTube IFrame API. The media is never proxied.

### Known deviations from the generated Park UI files

`@park-ui/cli@1.0.1` targets Panda v1. This project uses Panda v2 (the version that
ships the official `@pandacss/vite` plugin), so three manual fixes are required. They
are **overwritten** whenever `npx @park-ui/cli add …` runs, so re-apply them afterwards:

1. `src/components/ui/{dialog,field,select,tabs,toast}.tsx` — `createStyleContext` was
   renamed to `createSlotRecipeContext` in Panda v2.
2. `src/theme/recipes/input.ts` — `RecipeConfig` is imported from `@pandacss/types`
   instead of `@pandacss/dev`.
3. `src/theme/recipes/index.ts` — the CLI puts every recipe into `recipes`. The
   `defineSlotRecipe` recipes (`tabs`, `dialog`, `field`, `select`, `toast`) must live

Panda only emits the CSS of a recipe it can see being used. Because the Park UI
components are namespaced (`<Tabs.Root>`), `panda.config.ts` adds explicit `jsx`
hints for those recipes.

### Read API (issue #15)

The public read endpoints of `contracts/openapi.v1.yaml` are live. They use the
native Void route handlers and `void/db`; there is no second router.

| Route                                   | File                               | Behaviour                                                            |
| --------------------------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| `GET /api/v1/catalog`                   | `routes/api/v1/catalog.ts`         | Published songs, ordered by id, with `chartVersion` and `noteCount`. |
| `GET /api/v1/charts/{songId}?version=N` | `routes/api/v1/charts/[songId].ts` | Exactly that chart version, or 404.                                  |

`routes/api/v1/_read-model.ts` holds the shared response shapes (it is prefixed
with `_`, so Void does not turn it into a route).

Rules that the endpoints follow:

- **Published only.** A song is listed when `chart_versions` holds a row for
  `(songId, songs.currentVersion)`. A song row without a chart is not listed.
- **Stable order.** The catalog is ordered by song id.
- **`catalogVersion`** is the `catalog_meta` epoch (issue #656): every
  catalog-visible mutation — publish, archive, unarchive — bumps it inside
  the same transaction, so the value changes whenever the published catalog
  changes (archiving alone no longer leaves it still). Every producer —
  catalog, rankings, admin songs, publish and archive responses — serves
  the same value.
- **Exact versions.** `GET /api/v1/charts/{songId}` never falls back to the
  current version; an unknown version or song is 404.
- **`version` is required.** A missing, non-numeric or `< 1` version is 400.
- **`Cache-Control: no-store`** on both endpoints, because Unity polls the
  catalog every 5-10s and must never see a stale demo.

`node --test tests/` runs the integration test: it seeds the local D1, starts
the Void dev server, and validates the responses against the frozen contract
(`contracts/openapi.v1.yaml` and `contracts/schemas/chart.v1.schema.json`).

### Publish API (issue #16)

| Route                              | File                                    | Behaviour                                                 |
| ---------------------------------- | --------------------------------------- | --------------------------------------------------------- |
| `PUT /api/v1/admin/songs/{songId}` | `routes/api/v1/admin/songs/[songId].ts` | Staff-only atomic publication of a song + chart snapshot. |

- **Auth.** Bearer token compared against the `FLASHBEAT_ADMIN_TOKEN` runtime
  secret (`env.ts`) with a constant-time SHA-256 compare. The secret is
  provisioned from the FlashBeat Infisical project (`script/with-secrets`)
  into the Worker (`cf workers secrets update …`); it never appears in HTML,
  JS bundles, logs or commits. Wrong/missing token → `401`, checked before
  the body is read. There is no login UI.
- **Validation** (`routes/api/v1/_publish-model.ts`), two layers:
  1. Structure — the frozen contract schema (`SongPublishRequest` +
     `chart.v1`). The schema is bundled at build time (a Worker has no
     filesystem) and a unit test (`tests/publish-schema.test.ts`) fails when
     the bundled copy drifts from `contracts/openapi.v1.yaml`. The runtime
     validator is `@cfworker/json-schema` because Ajv compiles validators
     with `new Function`, which the Workers runtime forbids.
  2. Semantics — 8 lanes (`block` 0-7), positive beat positions (`num >= 0`,
     `LPB >= 1`), BPM 1-600, level 1-99, the note kinds (`type` 1 = Tap,
     `type` 2 = Hold with an `endNum` after its `num`), and every note inside
     `durationSec` using the Unity timing `num * 60 / (BPM * LPB)` (a Hold is
     measured at its `endNum`).
     Invalid input → `422` with `{ error, diagnostics: [{ path, message }] }`
     naming each offending item; nothing is written.
- **Publication.** One `db.batch` (a D1 implicit transaction) writes the song
  metadata upsert with `currentVersion + 1` (first publish = 1) and appends
  the immutable `chart_versions` row and bumps the `catalog_meta` epoch in
  the same batch. The response is
  `{ songId, chartVersion, catalogVersion, archived?, archivedAt? }` where
  `catalogVersion` is the epoch the read API serves, and the archive fields
  report that a republish of an archived song stays out of the catalog.
- **Local development.** Put a dev token in `.env` (gitignored) or export
  `FLASHBEAT_ADMIN_TOKEN` before `vp dev`; without it the Worker fails env
  validation at boot and every route returns 500.

The worker is deployed as `flashbeat-web` with the D1 binding of the
`flashbeat` database; `web/void.lock.json` pins both (including the
worker visibility — `workers_dev`/`preview_urls` — and the published-traffic
snapshot marker that a redeploy needs; do not strip them). The canonical
production hostname is **`https://flashbeat.rebuildup.dev`** (issue #9 domain
decision): a Custom Domain of the Worker, attached via
`routes: [{ pattern: "flashbeat.rebuildup.dev", custom_domain: true }]` in
`web/void.config.ts`, so Cloudflare owns the DNS record and the TLS
certificate. The autogenerated
`https://flashbeat-web.rebuild-up-up.workers.dev` stays enabled as fallback.
The publish endpoint (#16) is implemented, tested and live in production:
published songs are served by the read API at the same hostname.

### Publish screen (`/publish`)

The screen holds the metadata of one song next to the chart editor of issue #18 and
publishes both in one request.

- `src/lib/publish/validation.ts` holds the metadata rules of
  `contracts/openapi.v1.yaml` (`songId` pattern, title and artist length, video id,
  level `1`–`99`, duration `0`–`1800`). A broken field is marked before a request is
  built.
- `src/lib/publish/client.ts` is the typed client of
  `PUT /api/v1/admin/songs/{songId}`. The staff token travels as a bearer token in
  the request header. A failure is a value, not an exception: `401`, `404`, `422`,
  a broken answer and a request that never arrived are told apart.
- `src/lib/publish/mock.ts` is the fixture transport. It answers like the contract
  does, including the rejection of a chart that breaks the frozen chart schema.
  It writes nothing and is only a review aid.
- `src/lib/publish/transport.ts` picks the transport: the default is the API of the
  current origin (the studio and the API are the same worker), so a published song
  lands in the D1 of the deployment. `VITE_FLASHBEAT_API_ORIGIN` moves it to another
  origin — a public URL, the staff token is never part of it — and the explicit
  value `fixture` selects the fixture transport.
- The staff token is typed by the operator in the publish dialog. It stays in the
  memory of the browser tab and is never written to disk or to the bundle.
- The route is not server rendered (`ssr = false` in `pages/publish.server.ts`),
  because the chart editor draws into a canvas.

### Auth and ownership (issue #799, ADR-0036)

User accounts use **Void managed auth (Better Auth) on the same D1** —
`auth.ts` at the project root enables it; Void wires `/api/auth/*`, the
session middleware on every request, and `requireAuth`/`getSession`
(`void/auth`) / `auth` (`void/client`). `void db generate` emits the auth
tables (`user`, `session`, `account`, `verification`, `rateLimit`) into
`db/migrations/`; `BETTER_AUTH_SECRET` is optional in `env.ts` (Void
generates one on deploy, dev uses its built-in default). The threat model
is `docs/architecture/web-auth-threat-model.md` — read it before adding a
mutating route.

Ownership lives in two app tables next to the auth tables:

| Table               | Purpose                                                                             |
| ------------------- | ----------------------------------------------------------------------------------- |
| `workspaces`        | `kind='personal'` (`personal-<userId>`, lazy-provisioned) or `kind='team'`          |
| `workspace_members` | user ↔ workspace with role `owner`/`editor`/`viewer`; the only authorization source |
| `audit_log`         | append-only record of permission/publish/admin operations                           |
| `rate_limits`       | per-user fixed-window counters for the studio mutation APIs                         |
| `song_drafts`       | per-workspace working copy of a song (issue #800); never in the public catalog      |

`songs.ownerWorkspaceId` / `songs.createdByUserId` (nullable) mark
user-owned songs; existing rows stay `NULL` = staff-managed. The
per-account publish flow of issue #800 is documented below.

Rules every user-owned route follows (`routes/api/v1/_authz.ts`):

- identity comes from the session (`sessionUser`/`requireWorkspaceContext`),
  never from a client-supplied id; non-members get 404 (no existence leak);
- roles rank `owner > editor > viewer` (`hasWorkspaceRole`); member
  management is owner-only and `owner` is never grantable via the API;
  the last owner cannot be removed;
- request bodies go through `readJsonLimited` (`_request-body.ts`):
  Content-Length pre-check + streaming byte cap + JSON structure limits
  (depth/nodes/string) before parse.

| Route                                       | Behaviour                                   |
| ------------------------------------------- | ------------------------------------------- |
| `GET /api/v1/me`                            | session user + personal workspace (lazy)    |
| `GET/POST /api/v1/me/workspaces`            | list memberships / create a team workspace  |
| `GET/POST …/workspaces/{id}/members`        | list / add member by email (owner only)     |
| `DELETE …/workspaces/{id}/members/{userId}` | remove member (owner only, last-owner safe) |

`tests/authz.test.ts` is the negative contract suite (unauthenticated,
IDOR, role escalation, oversized/malformed bodies, XSS/SQLi payloads,
CSRF, concurrent adds, revoked session, rate limit, audit rows). The
node:test files share the local D1, so `npm test` runs them with
`--test-concurrency=1`.

### Account song flow (issue #800)

General users publish their own songs **without** `FLASHBEAT_ADMIN_TOKEN`.
The flow is draft → edit → publish; there is no separate "state" column —
a song is published iff `songs.currentVersion` points at a
`chart_versions` row, and unpublished by the same `archived` flag the
staff archive route uses.

| Route                                      | Behaviour                                                              |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| `GET /api/v1/me/songs`                     | caller's songs + drafts across all their workspaces                    |
| `POST /api/v1/me/drafts`                   | create a draft (`draft-<uuid>` id, optional `songId`, editor role)     |
| `GET/PUT /api/v1/me/drafts/{draftId}`      | read (viewer ok) / save working copy (editor+; chart stored leniently) |
| `POST /api/v1/me/drafts/{draftId}/publish` | publish/update; requires the rights attestation                        |
| `POST /api/v1/me/songs/{songId}/unpublish` | archive own song (公開停止); owner workspaces only, staff songs → 404  |

Decisions that must not regress:

- **Ownerless songs stay staff-managed.** `songs.ownerWorkspaceId NULL`
  rows are never listed in `/api/v1/me/songs`, never editable through the
  user routes, and — the IDOR fix — `PUT /api/v1/admin/songs/{songId}`
  answers **409** when the id belongs to a user workspace instead of
  silently overwriting it. Staff moderation of a user song goes through
  the archive route (`POST`), which has no ownership restriction.
- **Global slug namespace, first publisher wins.** `song_drafts.songId`
  has a UNIQUE index; create/publish re-check `songs` ownership, so a
  draft can never claim an id a `songs` row of another workspace (or a
  staff `NULL`-owned row) already holds → 409.
- **Rights are recorded, not assumed.** `songs.materialSource` /
  `rightsStatus` / `license` are nullable and stay `NULL` on staff rows.
  User publish requires `rightsConfirmed: true`, a non-empty
  `materialSource` and a `rightsStatus` of `original` / `licensed` /
  `permission` / `other` — missing → 422. The same fields stage on the
  draft so a resumed publish keeps them.
- **Publish is atomic.** One `db.batch` upserts the song (ownership +
  rights columns), appends the immutable `chart_versions` snapshot,
  advances `currentVersion`, stamps `publishedVersion` on the draft and
  bumps `catalog_meta`; audited as `song.publish` / `song.unpublish`.
- **Drafts are the resume source.** The chart editor opens a draft via
  `/chart?serverDraft=<draftId>` (`pages/chart.tsx` server-draft mode):
  the chart comes from D1, 「下書きを保存」 writes it back through
  `PUT /api/v1/me/drafts/{id}`, and publishing happens on `/my-songs`.
  The staff token hint and the sessionStorage publish-draft flow are
  unchanged for the staff routes.
- **UI.** `/login` (Void managed auth, `void/client/react`) and
  `/my-songs` (`src/app/my-songs-panel.tsx`) use the shared panel/list
  atoms; the sidebar gained a always-visible マイページ group plus an
  account widget — separate from the staff disclosure.

`tests/me-songs.test.ts` is the negative contract suite: unauthenticated
401s, cross-user/cross-workspace 404s, viewer 403s, missing rights → 422,
oversized bodies → 413, staff/user slug races → 409 both directions, and
the audit rows.

### Score API (issues #133, #578; ADR-0028)

| Route                                                          | File                                     | Behaviour                                                                                                                                       |
| -------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v1/scores`                                          | `routes/api/v1/scores.ts`                | Public score submission. The server **recomputes** the score from the submitted note counts, it never trusts the client.                        |
| `GET /api/v1/leaderboards/{songId}?version=N&scoringVersion=V` | `routes/api/v1/leaderboards/[songId].ts` | The best 10 scores of one chart version **and one scoring version**, score descending, the earliest submission wins a tie.                      |
| `GET /api/v1/rankings?scoringVersion=V`                        | `routes/api/v1/rankings.ts`              | The ranking board within one scoring version (default: the latest the server supports).                                                         |
| `GET /api/v1/stats`                                            | `routes/api/v1/stats.ts`                 | Festival statistics aggregated over the **latest** scoring version only — scores of different formula versions are never mixed (ADR-0028/0029). |

- `scoringVersion` selects the formula: `1` (or an omitted field — old clients)
  is `ratioScore = 5P+3G+B`, `maxScore = noteCount * 5`; `2` adds
  `comboBonus = maxCombo * 5` and `noMissBonus = (miss == 0) ? (P+G+B) * 5 : 0`
  with `maxScore = noteCount * 15`; `3` (ADR-0029) keeps the v2 components and
  adds `milestoneBonus = comboMilestones * 25` and
  `finalBonus = (miss == 0) ? 100 : 0` (a submission requires
  `perfect+great+bad+miss == noteCount`, so `miss == 0` already means the
  play completed — the same condition the Unity client vests the bonus on,
  Issue #618), with
  `maxRatio = noteCount * 15 + floor(noteCount / 50) * 25 + 100`.
- Since Issue #631 the score is **deterministic integer arithmetic**: every
  term is an integer and v3 ends in
  `score = floor(ratioScore * 1e6 / maxRatio)` (C# `long` division on Unity,
  IEEE-754 doubles here — identical because the operands stay far below
  2^53). Clients built before #631 still send the legacy single-precision
  (`Math.fround`) value; the server accepts it as an alternative but always
  stores the deterministic recomputation (`computeUnityScoreV3Legacy`).
- For `scoringVersion` 3 the server also verifies `maxCombo <= hits`
  (perfect+great+bad) and `comboMilestones`: exactly `floor(hits/50)` when
  `miss == 0` (one unbroken run), and at most
  `min(floor(hits/50), (miss + 1) * floor(maxCombo / 50))` when `miss > 0`
  (the exact crossing history is not reconstructible from the totals — the
  count stays a bound-checked client claim, ADR-0029). The server prices
  the count itself.
- `scores.scoringVersion` (integer, default 1, existing rows backfilled to 1)
  keeps the formulas apart: a submission is recomputed, ranked and
  aggregated only inside its own version. A `scoringVersion` the server cannot
  recompute is a 422; the leaderboard/rankings query parameter defaults to the
  latest version (currently 3). `comboMilestones` is ignored by versions 1
  and 2.

### Dashboard, statistics and the song archive (issue #151)

| Route                               | File                                    | Behaviour                                                                                          |
| ----------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `GET /api/v1/rankings?limit=N`      | `routes/api/v1/rankings.ts`             | The ranking board of every **live** song with its best scores (1-10 entries per song, default 10). |
| `GET /api/v1/stats`                 | `routes/api/v1/stats.ts`                | Totals, per song statistics, the level distribution and the best players.                          |
| `GET /api/v1/admin/songs`           | `routes/api/v1/admin/songs.ts`          | Staff-only list of every song, archived ones included, with plays and best score.                  |
| `POST /api/v1/admin/songs/{songId}` | `routes/api/v1/admin/songs/[songId].ts` | Staff-only archive / restore of one song.                                                          |

**Songs are never deleted.** The archive is a soft delete:

- `songs.archived` (`0`/`1`) and `songs.archivedAt` (ISO timestamp) are the only
  state. There is **no `DELETE` route** anywhere in the app.
- `GET /api/v1/catalog` filters on `archived = 0`, so an archived song leaves the
  Unity select screen. Its chart snapshots, its scores and its ranking survive.
- The archive route is idempotent and reversible: `{"archived": true}` archives,
  `{"archived": false}` restores. The body is validated by
  `routes/api/v1/_archive-model.ts` — a missing, non-boolean or unknown member is
  `422`, an unknown song is `404`, a wrong token is `401`.
- The staff list shows the archived songs with their archive timestamp and the
  play history, so an accidental archive can be undone.

The migration for the two columns is additive (`ALTER TABLE … ADD COLUMN`).
SQLite cannot add a `CHECK` constraint to an existing table, so the 0/1 invariant
lives in the API, not in the schema — see `db/schema.ts`.

`src/lib/dashboard/client.ts` holds the typed client and the **strict parsers**
of these answers: a broken field is an error, never a half filled table. The

The two pages are `ssr = false` (`pages/dashboard.server.ts`, `pages/songs.server.ts`):

### Copy and UI text

All user-facing strings of the studio — headings, button labels, loading, error
and empty states — are **Japanese** (unified in issue #611; the e2e and visual
selectors were updated to match). Copy quality follows the vendored
`natural-japanese` / `writing-discipline` skills (`.agents/skills/`,
`.claude/skills/`):

1. Audit the strings before writing; rewrite only the confirmed findings.
2. Smallest repair — the facts, the quantities and the register of the original stay.
3. No formulaic framing, no empty abstraction, no unsupported certainty, no repetition.
4. An error or a warning names the cause **and** the next action.

### Web guidance skill (issue #741)

`GoogleChrome/modern-web-guidance` was evaluated under the `skill-selection`
policy and **not installed** (ADR-0030): its Skill declares itself mandatory
for every HTML/CSS and client-side JS task — the broad, entry-grabbing trigger
the policy rejects — and its workflow delegates to an `npx` CLI that the
vendoring lock cannot pin. Its guides stay a **reference** for concrete
web-platform questions (accessibility, forms, UX patterns); consult them via
the upstream repo/CLI when a task calls for it, but do not vendor the Skill
or add the CLI as a dependency without re-running `skill-selection`.

### Studio information architecture (issue #742)

### Scope

The Web Studio has a database (issue #14), a read API (issue #15) and the publish
endpoint (issue #16) writes it. Both are deployed and live at
`https://flashbeat.rebuildup.dev`: the publish screen (issue #19) publishes into the
D1 of the deployment and the catalog of the shell reads the published songs from
`/api/v1/catalog`.

`?state=loading|empty|error` on `/` forces a list state so every branch of the
catalog panel can be reviewed without a backend.
