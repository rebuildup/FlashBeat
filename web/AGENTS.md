## FlashBeat Web Studio (`web/`)

Standalone web app for the festival build. It is **not** part of the Unity project and
the Unity project is never moved.

### Stack (locked)

Void (native routes + pages) · Vite+ (`vp`) · React 19 + TypeScript · Panda CSS
(`@pandacss/dev` + `@pandacss/vite`) · Park UI (`@ark-ui/react` + `@park-ui/cli`) ·
lucide-react · react-konva (chart grid) · Ajv (contract validation).
**Never install Tailwind, shadcn/ui or a second UI system.**

### Commands

```sh
vp install          # install dependencies (also runs `void prepare` + `panda codegen`)
vp dev              # dev server on http://localhost:5173
vp check            # format + lint (oxfmt / oxlint)
npx tsc --noEmit    # type check (TypeScript 7)
npm test            # node --test tests/ (read API) && vitest run (src/lib/**)
vp build            # production build
panda codegen       # regenerate styled-system after a panda.config.ts change
```

`styled-system/` is generated and gitignored. `postinstall` regenerates it, so a fresh
clone only needs `vp install`.

The unit tests run with `vitest.config.ts`, not with `vite.config.ts`: the Void plugin
starts a workerd inspector that cannot run inside the Vitest worker. The read API
integration test runs with `node --test tests/`, because it starts the real Void dev
server against the local D1.

### Database (D1)

The three festival tables live in `db/schema.ts` and are generated into
`db/migrations/` with Void's built-in Drizzle/D1 support:

| Table            | Purpose                                                             |
| ---------------- | ------------------------------------------------------------------- |
| `songs`          | Published song metadata plus the currently published chart version. |
| `chart_versions` | Immutable chart snapshot per `(songId, version)`.                   |
| `scores`         | Public score submissions.                                           |

```sh
void db generate     # regenerate db/migrations/ after a schema change
void db migrate      # apply pending migrations to the local D1
void db seed         # reset local D1, re-apply migrations, run db/seed.ts
void db status       # applied/pending migrations (local + deployment target)
node --test tests/  # read API integration tests (see "Read API")
```

The Cloudflare binding points at the single FlashBeat database
(`7de6fd23-dd7b-4e21-bddd-b28b33ee0462`) with `migrations_dir: "./db/migrations"`,
so `void db migrate --remote` and `cf d1 migrations apply` read the same SQL files
and share the `d1_migrations` bookkeeping table. Never reset the remote database:
ship a follow-up migration instead.

`db/fixtures/who.chart.json` is a byte-identical copy of the notes of
`Assets/Game/Resources/Who.json` (the `lyrics` block is not seeded)
and `db/fixtures/who.song.json` carries the matching metadata from
`Assets/Game/Scripts/Songs/GManager.cs`. The seed stores the chart file text
verbatim, so the published chart is identical to the one the Unity player ships.

### Chart editor (`/chart`)

The editor opens the legacy FlashBeat chart format
(`name`, `maxBlock`, `BPM`, `offset`, `notes[{type,num,block,LPB}]`, `lyrics`) and
writes it back unchanged.

- `src/lib/chart/` is pure logic: `import.ts` (read + validate), `export.ts` (write),
  `notes.ts` (edit operations), `timing.ts` (`60 / BPM * num / LPB`), `schema.ts`
  (Ajv against the frozen contract), `youtube.ts` (video id parsing).
- `src/lib/chart/chart.v1.schema.json` and `src/lib/chart/fixtures/sample-chart.json`
  are byte copies of `contracts/schemas/chart.v1.schema.json` and
  `Assets/Game/Resources/チュートリアル.json`. `.prettierignore` keeps the formatter
  away from them and `src/lib/chart/__tests__/contract-schema.test.ts` fails when they
  drift apart.
- The grid is `react-konva`. Konva needs a canvas, so the grid is loaded lazily and the
  route is not server rendered (`ssr = false` in `pages/chart.server.ts`).
- The preview is the YouTube IFrame API. The media is never proxied.

### Known deviations from the generated Park UI files

`@park-ui/cli@1.0.1` targets Panda v1. This project uses Panda v2 (the version that
ships the official `@pandacss/vite` plugin), so three manual fixes are required. They
are **overwritten** whenever `npx @park-ui/cli add …` runs, so re-apply them afterwards:

1. `src/components/ui/{dialog,field,select,tabs,toast}.tsx` — `createStyleContext` was
   renamed to `createSlotRecipeContext` in Panda v2.
2. `src/theme/recipes/input.ts` — `RecipeConfig` is imported from `@pandacss/types`
   instead of `@pandacss/dev`.
3. `src/theme/recipes/index.ts` — the CLI puts every recipe into `recipes`. The
   `defineSlotRecipe` recipes (`tabs`, `dialog`, `field`, `select`, `toast`) must live
   in `slotRecipes`, otherwise Panda drops their per-slot styles.

Panda only emits the CSS of a recipe it can see being used. Because the Park UI
components are namespaced (`<Tabs.Root>`), `panda.config.ts` adds explicit `jsx`
hints for those recipes.

### Read API (issue #15)

The public read endpoints of `contracts/openapi.v1.yaml` are live. They use the
native Void route handlers and `void/db`; there is no second router.

| Route                                   | File                               | Behaviour                                                            |
| --------------------------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| `GET /api/v1/catalog`                   | `routes/api/v1/catalog.ts`         | Published songs, ordered by id, with `chartVersion` and `noteCount`. |
| `GET /api/v1/charts/{songId}?version=N` | `routes/api/v1/charts/[songId].ts` | Exactly that chart version, or 404.                                  |

`routes/api/v1/_read-model.ts` holds the shared response shapes (it is prefixed
with `_`, so Void does not turn it into a route).

Rules that the endpoints follow:

- **Published only.** A song is listed when `chart_versions` holds a row for
  `(songId, songs.currentVersion)`. A song row without a chart is not listed.
- **Stable order.** The catalog is ordered by song id.
- **`catalogVersion`** is the number of published chart snapshots
  (`COUNT(chart_versions)`). Every publish adds a chart version, so the number
  changes whenever the published charts change. The publish endpoint (#16)
  must return the same value.
- **Exact versions.** `GET /api/v1/charts/{songId}` never falls back to the
  current version; an unknown version or song is 404.
- **`version` is required.** A missing, non-numeric or `< 1` version is 400.
- **`Cache-Control: no-store`** on both endpoints, because Unity polls the
  catalog every 5-10s and must never see a stale demo.

`node --test tests/` runs the integration test: it seeds the local D1, starts
the Void dev server, and validates the responses against the frozen contract
(`contracts/openapi.v1.yaml` and `contracts/schemas/chart.v1.schema.json`).

### Publish API (issue #16)

| Route | File | Behaviour |
| ----- | ---- | --------- |
| `PUT /api/v1/admin/songs/{songId}` | `routes/api/v1/admin/songs/[songId].ts` | Staff-only atomic publication of a song + chart snapshot. |

- **Auth.** Bearer token compared against the `FLASHBEAT_ADMIN_TOKEN` runtime
  secret (`env.ts`) with a constant-time SHA-256 compare. The secret is
  provisioned from the FlashBeat Infisical project (`script/with-secrets`)
  into the Worker (`cf workers secrets update …`); it never appears in HTML,
  JS bundles, logs or commits. Wrong/missing token → `401`, checked before
  the body is read. There is no login UI.
- **Validation** (`routes/api/v1/_publish-model.ts`), two layers:
  1. Structure — the frozen contract schema (`SongPublishRequest` +
     `chart.v1`). The schema is bundled at build time (a Worker has no
     filesystem) and a unit test (`tests/publish-schema.test.ts`) fails when
     the bundled copy drifts from `contracts/openapi.v1.yaml`. The runtime
     validator is `@cfworker/json-schema` because Ajv compiles validators
     with `new Function`, which the Workers runtime forbids.
  2. Semantics — 8 lanes (`block` 0-7), positive beat positions (`num >= 0`,
     `LPB >= 1`), BPM 1-600, level 1-99, Tap-only (`type` 1), and every note
     inside `durationSec` using the Unity timing `num * 60 / (BPM * LPB)`.
  Invalid input → `422` with `{ error, diagnostics: [{ path, message }] }`
  naming each offending item; nothing is written.
- **Publication.** One `db.batch` (a D1 implicit transaction) writes the song
  metadata upsert with `currentVersion + 1` (first publish = 1) and appends
  the immutable `chart_versions` row. The response is
  `{ songId, chartVersion, catalogVersion }` where `catalogVersion` is
  `COUNT(chart_versions)` — the same definition the read API serves.
- **Local development.** Put a dev token in `.env` (gitignored) or export
  `FLASHBEAT_ADMIN_TOKEN` before `vp dev`; without it the Worker fails env
  validation at boot and every route returns 500.

The worker is deployed as `flashbeat-web` with the D1 binding of the
`flashbeat` database; `web/void.lock.json` pins both (including the
worker visibility — `workers_dev`/`preview_urls` — and the published-traffic
snapshot marker that a redeploy needs; do not strip them). The canonical
production hostname is **`https://flashbeat.rebuildup.dev`** (issue #9 domain
decision): a Custom Domain of the Worker, attached via
`routes: [{ pattern: "flashbeat.rebuildup.dev", custom_domain: true }]` in
`web/void.config.ts`, so Cloudflare owns the DNS record and the TLS
certificate. The autogenerated
`https://flashbeat-web.rebuild-up-up.workers.dev` stays enabled as fallback.
The publish endpoint (#16) is implemented, tested and live in production:
published songs are served by the read API at the same hostname.

### Publish screen (`/publish`)

The screen holds the metadata of one song next to the chart editor of issue #18 and
publishes both in one request.

- `src/lib/publish/validation.ts` holds the metadata rules of
  `contracts/openapi.v1.yaml` (`songId` pattern, title and artist length, video id,
  level `1`–`99`, duration `0`–`1800`). A broken field is marked before a request is
  built.
- `src/lib/publish/client.ts` is the typed client of
  `PUT /api/v1/admin/songs/{songId}`. The staff token travels as a bearer token in
  the request header. A failure is a value, not an exception: `401`, `404`, `422`,
  a broken answer and a request that never arrived are told apart.
- `src/lib/publish/mock.ts` is the fixture transport. It answers like the contract
  does, including the rejection of a chart that breaks the frozen chart schema.
- `src/lib/publish/transport.ts` picks the transport: without
  `VITE_FLASHBEAT_API_ORIGIN` the fixture answers, with it the real endpoint does.
  The value is a public URL, the staff token is never part of it.
- The staff token is typed by the operator in the publish dialog. It stays in the
  memory of the browser tab and is never written to disk or to the bundle.
- The route is not server rendered (`ssr = false` in `pages/publish.server.ts`),
  because the chart editor draws into a canvas.

### Scope

The Web Studio has a database (issue #14), a read API (issue #15) and the publish
endpoint (#16) writes it. The publish screen (issue #19) publishes against the
fixture of `src/lib/publish/mock.ts` until the deployed endpoint is wired up;
`VITE_FLASHBEAT_API_ORIGIN` switches it to the real endpoint.

The catalog of the shell is still a local fixture in `src/app/catalog.ts`;
`?state=loading|empty|error` on `/` forces a list state so every branch can be
reviewed before the shell talks to the API.
