## 2. Schema

Three tables, defined in `web/db/schema.ts` with Void's built-in Drizzle/D1
support and generated into `web/db/migrations/`:

| Table | Columns | Notes |
|---|---|---|
| `songs` | `id`, `title`, `artist`, `youtubeId`, `bpm`, `level`, `durationSec`, `currentVersion` | `id` is the contract's `songId` (`^[a-z0-9-]{3,64}$`). |
| `chart_versions` | `songId`, `version`, `json`, `noteCount`, `createdAt` | Primary key `(songId, version)`, `json` holds the chart document. |
| `scores` | `id`, `songId`, `version`, `nickname`, `p`, `g`, `b`, `m`, `score`, `createdAt` | `p/g/b/m` are the perfect/great/bad/miss counts. |

Column names and types follow `contracts/openapi.v1.yaml` 1:1. The contract's
limits are enforced as SQLite `CHECK` constraints, so no client can store a row
the API contract would reject:

| Constraint | Rule |
|---|---|
| `songs_id_format` | length 3–64 and only `[a-z0-9-]` |
| `songs_title_length` | length 1–160 |
| `songs_artist_length` | length ≤ 160 |
| `songs_youtube_id_format` | length 11 and only `[A-Za-z0-9_-]` |
| `songs_bpm_range` | 1–600 |
| `songs_level_range` | 1–99 |
| `songs_duration_range` | `> 0` and `≤ 1800` |
| `songs_current_version_positive` | `≥ 1` |
| `chart_versions_version_positive` | `≥ 1` |
| `chart_versions_note_count_range` | `≥ 0` |
| `scores_version_positive` | `≥ 1` |
| `scores_nickname_length` | length 1–16 |
| `scores_judgments_non_negative` | `p/g/b/m ≥ 0` |
| `scores_score_range` | 0–1 000 000 |

`chart_versions.songId` and `scores.songId` reference `songs.id` with
`ON DELETE CASCADE`.

## 4. Local D1 (miniflare)

```sh
cd web
mise exec -- void db migrate   # applies the migration to .void/v3/d1/…
mise exec -- void db seed      # resets, re-applies, runs db/seed.ts
mise exec -- void db status    # → 20261106124714_heavy_harrier.sql  local: applied
```

Observed output after `void db seed`:

```

chart_versions
```

`jsonBytes = 5453` equals the byte length of `Assets/Resources/Who.json`; the
seed stores the file text verbatim, so the published chart is identical to the
chart the Unity player ships.

The local seed inserts the song and its chart version only. `scores` stays
empty on purpose: the score formula belongs to the scoring API (#20), so no
invented score is published.

## 5. Remote D1 (`flashbeat`)

Applied with the official Cloudflare CLI through the FlashBeat Infisical
project. `wrangler` is not used anywhere.

```sh
./script/with-secrets bash -c \
  'mise exec -- cf d1 migrations apply 7de6fd23-dd7b-4e21-bddd-b28b33ee0462 --dir web/db/migrations'
```

```
? About to apply 1 migration(s)
[ { "name": "20261106124714_heavy_harrier.sql", "status": "✅" } ]
```

Checks after the apply:

| Check | Result |
|---|---|
| `sqlite_master` tables | `chart_versions`, `d1_migrations`, `scores`, `songs` (+ `sqlite_sequence`) |
| `sqlite_master` indexes | `chart_versions_song_idx`, `scores_leaderboard_idx`, `sqlite_autoindex_chart_versions_1`, `sqlite_autoindex_songs_1` |
| `d1_migrations` | `id 1`, `20261106124714_heavy_harrier.sql`, applied `2026-11-06 12:54:38` |
| Column layout | identical to the table above on all three tables |
| `CHECK` constraints | present in the remote DDL (`songs_level_range` etc.) |
| Constraint enforcement | `INSERT … level = 100` → `[7500] CHECK constraint failed: songs_level_range: SQLITE_CONSTRAINT (extended: SQLITE_CONSTRAINT_CHECK)`; `SELECT COUNT(*) FROM songs` → `0`, nothing was written |

The remote database was **not** reset and **not** seeded: it only carries the
migration. The festival catalog is filled by the publish API (#16); a remote
reset would drop the migration history, so schema changes ship as follow-up
migrations.

## 6. Tests

```sh
cd web && npm test        # node --test tests/
```

`web/tests/db.test.mjs` builds a throw-away in-memory SQLite database from the
committed migration files and checks:

1. the chart fixture satisfies `contracts/schemas/chart.v1.schema.json`
   (ajv, draft 2020-12);
2. the migrations create exactly `songs`, `chart_versions` and `scores` with the
   contract's column names;
3. the seed publishes the chart file byte-identically and the note count matches
   the chart;
4. the schema rejects rows the contract rejects (song id, title, youtube id,
   bpm, level, duration, chart version, duplicate chart version, unknown song,
   nickname length, score range, negative judgments).

Result: 4 tests, 4 passed, 0 failed.
