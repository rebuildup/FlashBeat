## 2. Schema

Three tables, defined in `web/db/schema.ts` with Void's built-in Drizzle/D1
support and generated into `web/db/migrations/`:

| Table | Columns | Notes |
|---|---|---|
| `songs` | `id`, `title`, `artist`, `youtubeId`, `bpm`, `level`, `durationSec`, `currentVersion` | `id` is the contract's `songId` (`^[a-z0-9-]{3,64}$`). |
| `chart_versions` | `songId`, `version`, `json`, `noteCount`, `createdAt` | Primary key `(songId, version)`, `json` holds the chart document. |
| `scores` | `id`, `songId`, `version`, `nickname`, `p`, `g`, `b`, `m`, `score`, `createdAt` | `p/g/b/m` are the perfect/great/bad/miss counts. |

Column names and types follow `contracts/openapi.v1.yaml` 1:1. The contract's
limits are enforced as SQLite `CHECK` constraints, so no client can store a row
the API contract would reject:

| Constraint | Rule |
|---|---|
| `songs_id_format` | length 3–64 and only `[a-z0-9-]` |
| `songs_title_length` | length 1–160 |
| `songs_artist_length` | length ≤ 160 |
| `songs_youtube_id_format` | length 11 and only `[A-Za-z0-9_-]` |
| `songs_bpm_range` | 1–600 |
| `songs_level_range` | 1–99 |
| `songs_duration_range` | `> 0` and `≤ 1800` |
| `songs_current_version_positive` | `≥ 1` |
| `chart_versions_version_positive` | `≥ 1` |
| `chart_versions_note_count_range` | `≥ 0` |
| `scores_version_positive` | `≥ 1` |
| `scores_nickname_length` | length 1–16 |
| `scores_judgments_non_negative` | `p/g/b/m ≥ 0` |
| `scores_score_range` | 0–1 000 000 |

`chart_versions.songId` and `scores.songId` reference `songs.id` with
`ON DELETE CASCADE`.

## 8. Follow-up migration: the archive columns (issue #151)

Date: 2026-11-07 (JST) · Branch: `feature/web-dashboard-stats` · Scope: the soft
delete of a song. **No** remote D1 change has been applied yet.

### 8.1 The columns

| Column | Type | Rule |
|---|---|---|
| `songs.archived` | `integer NOT NULL DEFAULT 0` | `0` = live, `1` = archived. |
| `songs.archivedAt` | `text NULL` | ISO timestamp of the archive; `NULL` while the song is live. |

Plus the index `songs_archived_idx` on `songs(archived)`, used by the catalog
filter `WHERE archived = 0`.

**Why there is no `CHECK` constraint.** SQLite cannot add a `CHECK` constraint to
an existing table; drizzle-kit reacts by rebuilding the table
(`INSERT INTO __new_songs … SELECT archived … FROM songs`), which fails on a
fresh database because the old table has no such column. The 0/1 invariant is
therefore enforced in the API (`routes/api/v1/_archive-model.ts` and the archive
route), not in the table. This is the reason the migration is **additive**:

```sql
ALTER TABLE `songs` ADD `archived` integer DEFAULT 0 NOT NULL;
ALTER TABLE `songs` ADD `archivedAt` text;
CREATE INDEX `songs_archived_idx` ON `songs` (`archived`);
```
