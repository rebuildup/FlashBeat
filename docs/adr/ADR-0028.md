# ADR-0028: Scoring v2 (combo continuation and no-miss bonus) and scoringVersion Compatibility

- Status: Accepted
- Date: 2026-11-17
- Resolves: Issue #576; Issue #30 decision D5

## Context

The festival score today is the v1 formula implemented by Unity
(`Judge.ComputeScore`, `LongNote.ScoreFor`, `JudgeScoreboard`) and reproduced
server-side by the Web Worker (`web/routes/api/v1/_score-model.ts`
`computeUnityScore`):

```
judgment  = 5 * Perfect + 3 * Great + 1 * Bad
maxScore  = 5 * noteCount
score     = round(1_000_000 * judgment / maxScore)   // 1,000,000 cap kept
```

In v1 the combo counter is displayed but never feeds the score, so a play
with many misses can still reach a high score as long as its judgment counts
are good. The product decision (Issue #576) is to make combo continuation and
a no-miss clear bonus real scoring elements — **scoring v2** — while keeping
every score verifiable by the server from the submitted aggregate fields alone.

Code facts that constrain the formula (verified against the current
implementation, not assumed):

- `LongNote.ScoreFor` returns 5 / 3 / 1 for Perfect / Great / Bad
  (`LongNote.cs`).
- `JudgeScoreboard.ApplyHead` increments `Combo` for **all three** hit
  outcomes — Bad does **not** break the combo. `ApplyMiss` (time expiry) is
  the only path that resets `Combo` to 0.
  `DowngradeHoldToBad` replaces a head judgment with Bad but keeps the combo.
- A settled chart satisfies `Perfect + Great + Bad + Miss == noteCount`, and
  the server already enforces this in `scoreSemanticsDiagnostics`
  (`_score-model.ts`). `maxCombo` is optional but rejected when it exceeds
  `noteCount`.
- `maxScore = noteCount * 5` is set in `NotesManager` (`maxScore` is a float in
  Unity; the server emulates the single-precision rounding with `Math.fround`).
- Local persistence keys a best score by `ScoreKey = songId@chartVersion`
  (`ScoreKey.cs`, storage form `songId@chartVersion`), and D1 `scores` has no
  scoring-version column. Without a version marker, v1 and v2 records would
  overwrite and compare against each other even though they are different
  scales.

## Decision

### 1. Scoring v2 formula

For a play of a chart with `noteCount` notes (N = P+G+B+M):

```
judgment    = 5 * Perfect + 3 * Great + 1 * Bad          // unchanged from v1
comboBonus  = maxCombo * 5                              // 0 ≤ maxCombo ≤ N
noMissBonus = (miss == 0) ? (Perfect + Great + Bad) * 5 : 0
totalRatio  = judgment + comboBonus + noMissBonus
maxRatio    = 15 * noteCount                            // theoretical max
score       = round(1_000_000 * totalRatio / maxRatio)  // maxRatio <= 0 → 0
```

`maxRatio = 15 * N` is the sum of the three simultaneously achievable caps:
judgment ≤ 5N (all Perfect), comboBonus ≤ 5N (maxCombo ≤ N, enforced
server-side), noMissBonus ≤ 5N (all notes hit, miss = 0). A perfect run
reaches exactly 1,000,000.

Premises recorded as contract:

- **Miss** means time expiry only; it is the sole combo breaker. Bad keeps
  the combo (see code facts above), so `comboBonus` counts Bad-keeping runs.
- `maxCombo` is an aggregate the client reports; the server cross-checks only
  `maxCombo ≤ noteCount`, as it already does. The formula stays computable
  from `(P, G, B, M, maxCombo, noteCount)` — no combo history is needed.
- The 1,000,000 ceiling and the `score` range `0..1,000,000` are unchanged,
  so existing consumers of the field need no schema change beyond the new
  version marker.

### 2. scoringVersion

- `scoringVersion` is an **integer**. `1` = v1 formula, `2` = v2 formula.
- New clients always send `2`. Older clients that predate the field send
  nothing.
- `ScoreSubmission.scoringVersion` is **optional, minimum 1**. An omitted
  value is interpreted as `1`, preserving backward compatibility: old clients
  are accepted, recomputed with the v1 formula and stored as version 1. The
  server never rejects a submission solely because of its scoring version.
- The version selects which formula the server uses to recompute `score`;
  a mismatch between the client-declared formula's result and the stored row
  is still a 422, as today.

### 3. Separation of records

Three layers, one rule: **v1 and v2 records are never overwritten or ranked
together.**

- **Local (Unity `ScoreKey`)**: v2 records use the extended key form
  `songId@chartVersion@scoringVersion` (e.g. `songId@chartVersion@2`). Legacy
  keys `songId@chartVersion` are read as v1 records. The `@` separator remains
  unambiguous because song ids cannot contain `@`. No new record overwrites an
  old one: a v2 play writes only the `@2` key, a v1 play writes/updates only
  the bare key.
- **D1 `scores`**: add a `scoringVersion` column (`integer`, not null,
  default 1). Existing rows are backfilled to `1`. New submissions store the
  version they were scored under.
- **Ranking / statistics**: `GET /api/v1/leaderboards/{songId}` and
  `GET /api/v1/rankings` accept an optional `scoringVersion` query parameter.
  When omitted, the server uses the latest scoring version it supports
  (currently `2`), so boards default to the current formula and never mix
  versions. `GET /api/v1/stats` aggregates **only the latest scoring version**
  — mixing v1 and v2 scores in `plays`, `averageScore`, `bestScore` and
  `topPlayers` would silently compare different scales; v1 rows remain
  readable through the versioned leaderboard query.

### 4. Client-visible breakdown (contract note)

v2 needs the client to surface the bonus components during play, on
accumulation and on the result screen. The submitted fields stay
`(P, G, B, M, maxCombo, score)` — the server never trusts a client-reported
bonus breakdown. For local display and result rendering the client computes
`comboBonus` / `noMissBonus` itself from the same fields it already tracks;
no additional submission fields are introduced by this ADR. If a later
requirement needs per-component history (e.g. "combo bonus earned at time T"),
that is a new contract change, not part of v2.

## Alternatives considered and rejected

- **Sequential combo-history bonus** (e.g. +k per consecutive hit): rejected.
  It depends on the order/timing of hits, which the aggregate submission
  fields cannot express, so the server could not recompute it and the
  anti-manipulation guarantee of "server recomputes everything" would break.
- **Client-reported bonus breakdown**: rejected for the same reason — the
  server would have to trust unverifiable fields.
- **Separate `scores_v2` table or composite `(songId, chartVersion,
  scoringVersion)` key without a column**: rejected in favor of a nullable-
  free `scoringVersion` column with backfill; a column keeps every existing
  query shape and lets the version filter live in one place.
- **Rejecting v1 clients**: rejected. Festival builds in the field may lag the
  contract; treating a missing `scoringVersion` as `1` costs nothing and
  keeps old submissions valid.
- **Mixing v1/v2 in stats**: rejected (see §3) — aggregates across different
  scoring scales are meaningless.

## Consequences

- Unity implementation Issue: compute v2 in `JudgeScoreboard`/`Judge`, extend
  `ScoreKey` with the `@version` form, send `scoringVersion: 2` in
  `ScoreSubmission`, display the bonus breakdown locally and on the result
  screen.
- Web implementation Issue: extend `SCORE_SUBMISSION_SCHEMA` and
  `ScoreSubmission`, recompute per declared version, add the
  `scoringVersion` column migration with backfill, add the query parameter to
  leaderboard/rankings, restrict stats to the latest version.
- `score` maximum stays 1,000,000 everywhere; no consumer cap changes.
