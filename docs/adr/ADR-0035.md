# ADR-0035: Scoring v5 (milestone-only combo bonus) and scoringVersion 5

- Status: Accepted
- Date: 2026-11-21
- Resolves: Issue #797 (parent Program Issue #803); builds on ADR-0033 (v4
  formula) and ADR-0034 (v4 grade bands); related Issue #788 (grade/gauge
  consistency), Issue #784 (combo bonus visibility)
- Related: ADR-0028 / ADR-0029 (v1–v3 contracts, unchanged),
  ADR-0033 (v4 contract, unchanged for scoringVersion ≤ 4 records)

## Context

The v0.2.3 real-device review (Issue #797) rejected the v4 bonus shape:

> 現行スコア v4 は `maxCombo * 5` の連続加点と 50 コンボ単位の
> マイルストーン加点が共存しており、要求と異なる。

The requested model is **milestone-vested**: score is added only when a
combo milestone is reached, and a gauge shows progress toward the next
milestone. v4 cannot express this — `comboBonus = maxCombo * 5` grows
continuously with the longest run and the milestone term (25 ratio points
per crossing) is a minor add-on, so "reaching 50/100/150 combo" has no
distinct score event.

Because the meaning of `score` changes, this is a new `scoringVersion`.
v1–v4 records are never recomputed or reinterpreted (the ADR-0028 §3
separation rule carries over).

Code facts that constrain the design (verified against the implementation):

- `JudgeScoreboard.ApplyHead` already counts exactly one
  `MilestoneCrossings` increment per combo multiple of
  `Scoring.MilestoneInterval` (50) reached, on the single head-judgment
  path — one note can never double-count, and crossings **accumulate**
  across combo breaks (`Combo` resets on Miss, `MilestoneCrossings` does
  not). Re-reaching the same milestone value after a break is a *new*
  crossing event and pays again; it is not a duplicate of the earlier
  event. The server bound checks (`miss == 0` → exact
  `floor(hits/50)`; `miss > 0` → `(miss+1) * floor(maxCombo/50)` run bound)
  remain valid for v5 unchanged.
- The sum of `floor(runLength / 50)` over all runs is always ≤
  `floor(hits / 50)`, so no miss pattern can exceed the milestone cap —
  deliberately breaking combo never increases the milestone count.
- `maxCombo` stays in the submission contract (it is still bound-checked
  and used for statistics), but v5 does not price it.

## Decision

### 1. Scoring v5 formula

Constants: `MILESTONE_INTERVAL = 50` (unchanged),
`MilestoneBonusPointsV5 = 250` (new — see §1.1),
`FULLCOMBO_BONUS = 100` (unchanged), per-note judgment weights unchanged.

For a play of a chart with `noteCount` notes (N), `hits = P+G+B`:

```
judgment        = 5 * Perfect + 3 * Great + 1 * Bad          // unchanged
comboBonus      = — (removed: continuous combo pays nothing) // NEW in v5
noMissBonus     = (miss == 0) ? hits * 5 : 0                 // unchanged
milestoneBonus  = comboMilestones * 250                     // was * 25 in v4
finalBonus      = judgmentsComplete && (miss == 0) ? 100 : 0 // unchanged

baseScore       = floor(judgment * 1_000_000 / (5N))          // ≤ 1,000,000 (unchanged)
bonusRatio      = milestoneBonus + noMissBonus + finalBonus   // no comboBonus term
maxBonusRatio   = floor(N/50) * 250 + 5N + 100                // v4: 10N + floor(N/50)*25 + 100
bonusScore      = floor(bonusRatio * 1_000_000 / maxBonusRatio) // ≤ 1,000,000
score           = baseScore + bonusScore                      // ≤ 2,000,000
```

All arithmetic is exact integer math (`long` on Unity, IEEE-754 doubles on
the Worker), identical on every platform — the Issue #631 property carries
over unchanged.

#### 1.1 Why `MilestoneBonusPointsV5 = 250`

The removed `comboBonus` had a theoretical cap of `5N` ratio points
(`maxCombo ≤ hits ≤ N`). The milestone mechanism inherits that budget:
`floor(N/50) * 250 ≈ 5N` (exactly `5N` up to the `N mod 50` remainder).
Choosing 250 keeps the **total combo-derived bonus ceiling unchanged**
while restructuring *when* it vests: instead of accruing continuously
with `maxCombo`, it vests in discrete milestone events. Smaller values
(25 — the v4 rate — or 100) were rejected because the milestone popup and
the bonus half would become nearly invisible: on a 500-note chart one
crossing would add ~9k (25 pts) to ~35k (100 pts) score points out of
2,000,000, defeating the purpose of the feature; 250 gives ~+49,000 per
crossing on that chart — clearly readable, still bounded.

#### 1.2 Consequences of the shape

- **Every completed `miss == 0` play (judgmentsComplete — i.e. every
  submitted/result play) scores exactly the same total as under v4.**
  With no misses the combo never breaks, so `maxCombo = hits = N` and
  `comboMilestones = floor(N/50)`; both formulas then saturate their
  bonus halves (`bonusRatio == maxBonusRatio` → `bonusScore =
  1,000,000`) and `baseScore` is judgment-only and identical. The v5
  change therefore only re-prices plays that contain misses — the
  no-miss ladder (all-Perfect FC = 2,000,000 = SS) is untouched.
  (In-progress live projections with `miss == 0` can differ slightly
  because the denominators are chart-size based; that display path is
  not a stored score.)
- **Miss plays keep their earned milestones.** Crossings already banked
  before a break are never revoked; after the break the gauge refills
  from 0 and the next crossing pays again. This matches the Issue #797
  requirement that earned bonuses survive a combo break while the combo
  itself resets.
- **No double-processing.** A crossing is an event, counted once in
  `ApplyHead`; `MilestoneCrossings` is monotonic. The HUD detects gains
  by delta (`GManager.comboMilestones - lastComboMilestones`), so a
  repeated value can never re-trigger the popup.
- **`maxCombo` is still submitted** (contract field, bound-checked
  `≤ hits`) but no longer enters the score; it remains available for
  statistics and the milestone bound check.

### 2. scoringVersion and record separation

- `scoringVersion = 5` selects the v5 formula; new Unity clients send 5
  and the server's `LATEST_SCORING_VERSION` becomes 5. Omitted still
  means 1.
- `ScoreKey` needs no format change; v5 records use `@5`.
- D1 needs **no migration**: the existing `scores_score_range` CHECK
  (`score ≤ 2,000,000 AND (scoringVersion >= 4 OR score ≤ 1,000,000)`)
  already admits v5 rows.
- Leaderboards, rankings and stats keep filtering by `scoringVersion`;
  the default scope becomes 5. v4 boards remain queryable via
  `?scoringVersion=4`.
- The submission `score` field keeps `maximum: 2000000`; per-version caps
  are enforced by recomputation as before.

### 3. Grade bands (unchanged thresholds, re-validated for v5)

v5 keeps the Issue #788 bands — `SS = 2,000,000`, `S ≥ 1,900,000`,
`A ≥ 1,400,000`, `B ≥ 1,000,000` — because:

- No-miss plays are score-identical to v4 (§1.2), so the top of the
  ladder is unchanged by construction.
- Simulation across the catalog note counts (53–603) and judgment/miss
  mixes shows miss-inclusive normal plays spread across B and A rather
  than collapsing into C: a single late miss with good judgments lands
  ~1.24–1.49M (B, top end A on larger charts), ~5 spread misses with good
  judgments ~0.98–1.46M (B/C boundary), ≥10 misses ~0.58–1.43M depending
  on chart size and judgment quality, and poor-judgment plays stay in C.
  S/SS remain no-miss-only grades.
- Lowering A (e.g. 1.3M) was rejected: it would promote ~5-miss plays
  and weak-judgment plays into A, making the grade common. Raising B was
  rejected for the symmetric reason. The v4 thresholds already sit at the
  distribution's natural breaks for the v5 shape.

Because the bands are identical, `V6GradeLogic` needs no new threshold
constants — `GradeOf`/`GradeOfV4` already produce the v5 grades, and the
gauge normalization (`ScoreMaxOf` → 2,000,000 for `scoringVersion >= 4`)
is correct for v5 unchanged. The grade/gauge consistency contract of
Issue #788 therefore carries over: the gauge fill is `score / 2,000,000`
of the rail and the grade letter comes from the same score on the same
scale.

### 4. Client-visible contract (Unity + Web share one spec)

- **HUD combo bonus block** shows the *earned milestone total* in score
  points (`ComponentScoreV5(milestoneBonus, maxBonusRatio)`), the *next
  milestone progress* gauge (`combo % 50 / 50` — already implemented as
  `V6HudLogic.ComboFillFraction`), and the *per-crossing gain* popup
  (`+gained  TOTAL +earned`). Earned total, this gain and next gain are
  three distinct values and are displayed as such; the next crossing is
  always worth `ComponentScoreV5(250, maxBonusRatio)` score points.
  The block is visible whenever a next milestone is still reachable —
  i.e. while `chartNoteCount - settledNoteCount` can still supply the
  `50 - (combo % 50)` consecutive hits needed (`V6HudLogic.
  NextMilestoneReachable`) — or once any milestone has been earned
  (earned bonus survives a miss). A play that ends with zero crossings
  never shows a phantom "next" award.
- **Result breakdown** shows BASE (judgment, ≤1M) / COMBO (–, no
  continuous bonus exists in v5) / MILESTONE (earned crossings) / CLEAR
  (no-miss + full-combo) — each converted with the v5 bonus denominator.
- **Web** recomputes v5 submissions with `computeUnityScoreV5` using the
  identical integer formula; the `comboMilestones` bound checks are
  applied to v5 exactly as for v3/v4.

## Alternatives considered and rejected

- **Keep `MilestoneBonusPoints = 25`**: rejected — the milestone bonus
  becomes a rounding error (~1% of the bonus half on catalog charts) and
  the requested "reach a milestone, get score" experience is imperceptible.
- **Keep `maxCombo` in the formula alongside milestones**: rejected —
  that is exactly the v4 dual-track the review rejected; continuous combo
  accrual must not exist in v5.
- **Per-crossing escalating values** (e.g. later milestones worth more):
  rejected — adds a second axis of complexity for no contract benefit;
  uniform 250 keeps the server recompute and HUD popup trivially
  explainable.
- **New grade bands for v5**: rejected — see §3; identical thresholds
  keep v4/v5 grades comparable and the distribution already fits.
- **Revise v4 in place**: rejected — stored v4 scores would silently
  change meaning; version separation is the established mechanism.

## Consequences

- **Unity**: `Scoring` gains `Version5`/`LatestVersion = 5`,
  `MilestoneBonusPointsV5`, `MaxBonusRatioV5`, `V5Breakdown`/
  `BreakdownV5`/`ScoreV5`/`ComponentScoreV5`. `Judge.FlushScore` scores
  through v5; `GManager.comboBonus` is no longer populated (v5 has no
  continuous combo bonus — the HUD reads `milestoneBonus` for the earned
  total). `JudgeScoreboard` is unchanged. HUD/result/select grade paths
  dispatch on `Scoring.LatestVersion` and need only the v5 component
  conversions.
- **Web**: `SCORING_VERSION_V5`, `LATEST_SCORING_VERSION = 5`,
  `computeUnityScoreV5`, v5 in the milestone bound checks and the
  per-version score cap, `computeScoreForVersion` dispatch, contract
  (`openapi.v1.yaml`) descriptions, parity vectors (`scoreV5`/
  `scoreV5Settled`).
- **Compatibility**: v1–v4 submissions, records, boards and stats are
  untouched; old clients keep working. `scoringVersion=4` records are
  never reinterpreted as v5 and vice versa.
- **D1**: no migration required (§2).

## Verification obligations

- `baseScore ≤ 1,000,000`, `bonusScore ≤ 1,000,000`, `score ≤ 2,000,000`
  for every input including boundary note counts — contract tests on both
  sides.
- Perfect full-combo = exactly 2,000,000; every completed `miss == 0`
  play scores identically under v4 and v5 formulas (property-tested).
- Combo contract: a play with only combo continuation and no milestone
  crossing earns zero combo bonus; each crossing adds
  `ComponentScoreV5(250)` ratio→score points (the floored total can make
  the marginal display ±1 point — the HUD popup reports the floored
  delta of the accumulated total, not a per-event constant); crossings
  survive misses; no event double-counts
  (`ApplyHead` once per note; `MilestoneCrossings` monotonic).
- Independent acceptance oracle: representative plays (perfect FC,
  high-Great FC, single late miss, spread misses, HOLD-heavy, all-Bad)
  are scored by hand-computed expectations in tests — not generated from
  the formula under test — and the distribution table above is reproduced
  in the ADR for review.
- Parity: `contracts/parity/score-vectors.json` gains `scoreV5` /
  `scoreV5Settled`; Unity `ParityFixtureTests` and Web
  `parity-score.test.ts` assert them exactly.
- Server: a legitimate v5 score > 1,000,000 is accepted (201); a v5
  submission disagreeing with recomputation is rejected (422); v1–v4
  submissions claiming v5-range scores under their own version are still
  rejected.
- Grades/gauge: v5 scores grade under the §3 bands; `ScoreMaxOf(5) =
  2,000,000`; gauge fill and grade letter derive from the same score.
- `scoringVersion=4` local records (`@4`) and remote rows are untouched;
  v5 records use `@5`.

## Distribution evidence (simulation, catalog N = 53–603)

`score = baseScore + bonusScore` evaluated for judgment mixes
(all-Perfect → all-Bad, incl. P/G/B blends) × miss scenarios
(0, 1, 2, 3, 5, 10, 20 spread evenly; `maxCombo` = longest run,
`comboMilestones` = Σ floor(run/50)). Representative v5 scores
(P5 = 250), with the v4 score of the same play in parentheses:

| Play (N=500 unless noted) | v5 score | v4 score |
| --- | --- | --- |
| All-Perfect FC | 2,000,000 | 2,000,000 |
| 90P/10G FC | 1,960,000 | 1,960,000 |
| All-Great FC | 1,600,000 | 1,600,000 |
| All-Bad FC | 1,200,000 | 1,200,000 |
| All-Perfect, 1 miss (mid) | 1,437,176 | 1,193,196 |
| 90P/10G, 1 miss | 1,399,176 | 1,153,196 |
| 80P/20G, 3 misses | 1,262,626 | 1,069,005 |
| 70P/30G, 5 misses | 1,132,469 | 977,207 |
| 50P/50G, 10 misses | 784,000 | 826,056 |
| All-Great, 5 misses | 854,869 | 699,607 |
| All-Perfect, 20 misses | 960,000 | 981,495 |
| All-Bad, any misses | ≤ ~690,000 | ≤ ~480,000 |

Reading: no-miss plays are identical by construction; miss plays trade
the truncated `maxCombo` term for fully-earned milestone crossings, so
good-combo plays score moderately higher than v4 while heavy-miss plays
converge to the judgment-only base. Grade bands (SS = 2M / S ≥ 1.9M /
A ≥ 1.4M / B ≥ 1.0M) put typical miss-inclusive plays in B–A and keep
S/SS miss-free.
