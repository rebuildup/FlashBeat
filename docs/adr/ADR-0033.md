# ADR-0033: Scoring v4 (base score capped at 1,000,000 plus additive bonuses) and scoringVersion 4

- Status: Accepted
- Date: 2026-11-21
- Resolves: Issue #736 (parent Epic #728 item 8); supersedes the v3 *normalization* for new clients
- Related: ADR-0028 (v1/v2 contract, unchanged), ADR-0029 (v3 contract, unchanged for scoringVersion 1–3 records); Issue #631 (deterministic integer scoring)

## Context

ADR-0029 scoring v3 computes

```
score = floor(totalRatio * 1_000_000 / maxRatio)
maxRatio = 15N + floor(N/50)*25 + 100
```

which **normalizes the whole play — judgment and every bonus — into a single
1,000,000 ceiling**. A perfect run reaches exactly 1,000,000 and no play can
exceed it, so the combo / milestone / no-miss / full-combo bonuses can never
push a score past the cap. The product contract (owner decision, Issue #728
item 8 / Issue #736) is different:

> 基礎スコア上限 = 1,000,000（判定由来のみ）。コンボ・マイルストーン等の
> ボーナスはその上に独立加算し、フルコンボの最終スコアは 1,000,000 を超える。

In other words the judgment-derived part keeps the 1,000,000 ceiling and the
bonuses are **added on top**, so a full-combo run legitimately exceeds
1,000,000. Because the meaning of `score` changes, this is a new
`scoringVersion` — v1–v3 records are never recomputed or reinterpreted
(ADR-0028 §3 separation rule carries over unchanged).

Code facts that constrain the design (verified against the implementation):

- Every v3 bonus component is already an integer number of ratio points and
  every bound the server checks (`maxCombo ≤ hits`, the `comboMilestones`
  exact/run bound of ADR-0029 §2 as amended by #618) is version-agnostic —
  v4 reuses them verbatim.
- `judgment = 5P + 3G + B ≤ 5N` always, with equality iff every note is
  Perfect and none missed. So `floor(judgment * 1e6 / (5N))` is ≤ 1,000,000
  by construction and equals 1,000,000 exactly for an all-Perfect play.
- `bonusRatio = comboBonus + noMissBonus + milestoneBonus + finalBonus` is
  bounded by `10N + floor(N/50)*25 + 100` under the same submission checks:
  `comboBonus ≤ 5N` (maxCombo ≤ hits ≤ N), `noMissBonus ≤ 5N` (only when
  miss = 0, then hits = N), `milestoneBonus ≤ floor(N/50)*25`,
  `finalBonus ≤ 100`.
- All v3 scoring is deterministic integer arithmetic (Issue #631); v4 keeps
  that property — no floats anywhere in the score path.

## Decision

### 1. Scoring v4 formula

Constants are inherited unchanged from ADR-0029:

```
MILESTONE_INTERVAL = 50
MILESTONE_BONUS    = 25    // ratio points per crossing
FULLCOMBO_BONUS    = 100   // ratio points, once at judgmentsComplete && miss == 0
```

For a play of a chart with `noteCount` notes (N = P+G+B+M), `hits = P+G+B`:

```
judgment       = 5 * Perfect + 3 * Great + 1 * Bad          // unchanged
comboBonus     = maxCombo * 5                              // unchanged (ratio points)
noMissBonus    = (miss == 0) ? hits * 5 : 0                // unchanged
milestoneBonus = comboMilestones * 25                      // unchanged
finalBonus     = judgmentsComplete && (miss == 0) ? 100 : 0 // unchanged

// --- base: judgment-derived only, hard ceiling 1,000,000 ---
baseRatio      = judgment                                  // ≤ 5N
baseScore      = floor(baseRatio * 1_000_000 / (5N))        // ≤ 1,000,000;
                                                        // all-Perfect → exactly 1,000,000

// --- bonus: the v2/v3 bonus components, normalized to their own ceiling ---
bonusRatio     = comboBonus + noMissBonus + milestoneBonus + finalBonus
maxBonusRatio  = 10N + floor(N/50) * 25 + 100               // theoretical max of bonusRatio
bonusScore     = floor(bonusRatio * 1_000_000 / maxBonusRatio) // ≤ 1,000,000

score          = baseScore + bonusScore                    // ≤ 2,000,000
```

All arithmetic is exact integer math (`long` on Unity, IEEE-754 doubles on
the Worker — every intermediate is a small integer, identical on every
platform, same argument as Issue #631).

A **perfect full-combo run scores exactly 2,000,000**: base 1,000,000
(all-Perfect judgments) + bonus 1,000,000 (every bonus component at its cap).
A completed no-miss play always reaches `bonusScore = 1,000,000` — with
`miss == 0` the combo never breaks, so `maxCombo = hits = N`,
`comboMilestones = floor(N/50)` (verified exactly by the server) and
`finalBonus = 100`, i.e. `bonusRatio = maxBonusRatio` — and its total is
`baseScore + 1,000,000`, ranging from 1,200,000 (all-Bad clear) to
2,000,000 (all-Perfect). Plays with misses get a partial `bonusScore` scaled
by `maxCombo` and the milestone count, so the bonus still differentiates
imperfect runs.

#### 1.1 Why this shape

- **Judgment-only base**: the owner contract says the 1,000,000 ceiling
  belongs to the judgment-derived score. `5N` is the same per-note judgment
  cap v1 used (`maxScore = noteCount * 5`), so the base is the familiar v1
  score with deterministic integer rounding.
- **Bonus normalized to its own ceiling**: `maxBonusRatio` is the exact sum
  of the simultaneously achievable bonus caps (5N combo + 5N no-miss +
  milestone cap + 100), mirroring how v2/v3 built `maxRatio` from component
  caps. A perfect bonus profile therefore converts to exactly 1,000,000
  bonus points — the "full combo adds a million" reading is exact, not
  approximate.
- **Two floors, not one**: `baseScore` and `bonusScore` are each floored
  once; `score = baseScore + bonusScore`. This keeps `baseScore ≤ 1,000,000`
  and `bonusScore ≤ 1,000,000` independently provable, which is what the
  contract asserts. The components do not have to sum to anything else.
- **Bonus ≥ 0**: every bonus term is non-negative by construction.

#### 1.2 Semantics kept from v3

- `comboMilestones` vesting, the milestone interval/points, the
  `judgmentsComplete && miss == 0` condition of `finalBonus`, the
  "Bad keeps the combo / only time-expiry Miss breaks it" premise and the
  server-side bound checks (`maxCombo ≤ hits`; `comboMilestones` exact when
  `miss == 0`, `(miss + 1) * floor(maxCombo/50)` run bound otherwise) are
  **unchanged** — v4 applies the identical checks.
- v1–v3 submissions, records, boards and stats are untouched; a missing
  `scoringVersion` still means 1.

### 2. scoringVersion and record separation

- `scoringVersion = 4` selects the v4 formula; new Unity clients send 4 and
  the server's `LATEST_SCORING_VERSION` becomes 4. Omitted still means 1.
- `ScoreKey` is already version-agnostic (`songId@chartVersion@scoringVersion`,
  bare = v1) — no format change; v4 records simply use `@4`.
- D1 `scores.scoringVersion` already exists; the score range CHECK is
  relaxed by a follow-up migration (see §4). Leaderboards, rankings and
  stats keep filtering by `scoringVersion`; the default scope becomes 4.
- The submission `score` field accepts up to 2,000,000. Per-version caps are
  still enforced: v1–v3 recomputations can never exceed 1,000,000, so a
  v1–v3 submission claiming more fails the score cross-check (422), and the
  DB CHECK keeps `score ≤ 1,000,000` for `scoringVersion < 4` rows.

### 3. Client-visible breakdown

- In play, the milestone popup keeps reporting the gained bonus in score
  points, now converted with the v4 bonus denominator
  (`floor(ratioPoints * 1e6 / maxBonusRatio)`), and stays visible long
  enough to read (see §5).
- The result screen shows the **base score** (judgment-derived, ≤ 1M) next to
  the bonus components (combo / milestone / clear = no-miss + full-combo),
  each as the score points it actually added. These are display estimates of
  the same integer components the server recomputes — never submission
  fields.

### 4. D1 migration

SQLite cannot alter a `CHECK` constraint, so the `scores_score_range` check
(`score BETWEEN 0 AND 1000000`) is replaced by rebuilding the `scores` table:

```
score >= 0
AND score <= 2000000
AND (scoringVersion >= 4 OR score <= 1000000)
```

Existing rows are copied verbatim (all ≤ 1,000,000, all `scoringVersion ≤ 3`,
so they satisfy the new check). The remote apply is a separate operational
step recorded in `docs/operations/d1-migrations.md`; this change only ships
the migration file.

### 5. Bonus display readability

The milestone bonus popup previously faded after 1.2 s — too short to read a
comma-separated score gain while notes keep falling. The display lifetime is
now defined from readability reasoning, not shrinkage:

- A "+12,345"-class gain needs roughly 0.5–0.8 s of dwell for a player to
  foveate and parse the digits; HUD toasts conventionally dwell ≥ 1.5 s.
- Milestones can recur every ~50 combo (several seconds apart on catalog
  charts), so a longer dwell does not stack duplicates in practice; when it
  does, the newest value simply replaces the text.
- `MilestoneBonusSeconds` is therefore **2.5 s** total (full alpha for most
  of it, eased fade at the end), documented as a readability constant.

## Alternatives considered and rejected

- **Revise v3 in place (same scoringVersion=3, uncapped score)**: rejected —
  v3 records on devices and D1 would silently change meaning; ADR-0028's
  version separation exists exactly for this.
- **Keep one shared denominator and just raise the cap** (e.g.
  `score = floor(totalRatio * 2e6 / maxRatioV3)`): rejected — the judgment
  part would no longer have a clean 1,000,000 ceiling; "base ≤ 1M" would
  stop being provable from the formula.
- **Add raw bonus ratio points to the base score without normalization**
  (e.g. `baseScore + bonusRatio`): rejected — bonus scale would depend on
  chart length in an unbounded way and a small chart's bonus would dwarf the
  judgment score; the per-version ceiling story breaks.
- **Normalize bonus to a smaller fixed cap (e.g. +250,000)**: rejected —
  arbitrary constant with no lineage; the bonus components already have a
  natural theoretical maximum, and "full combo = +1,000,000" is the
  clearest possible contract.
- **Grade thresholds redesigned for v4**: deferred — the grade bands are a
  separate product contract; this ADR only notes that the result screen
  maps the v4 scale (max 2,000,000) so a perfect run still earns SS.

## Consequences

- **Unity** (#736): `Scoring` gains `Version4`/`LatestVersion = 4`,
  `BreakdownV4`/`ScoreV4` (integer math), `MaxBonusRatioV4` and the bonus
  component display conversion; `Judge.FlushScore` writes the v4 breakdown
  and the new `GManager.baseScore`/`bonusScore`/`maxBonusRatio` fields;
  `RankingClient` sends `scoringVersion: 4`; the HUD milestone popup uses
  the v4 conversion and the longer lifetime; the result bonus line shows
  base vs bonus.
- **Web** (#736): `computeUnityScoreV4`, `SCORING_VERSION_V4`,
  `LATEST_SCORING_VERSION = 4`, submission `score` maximum 2,000,000 with
  the v1–v3 cap still enforced by recomputation (and explicitly diagnosed),
  the same milestone/maxCombo bound checks applied to v4, OpenAPI maximums
  updated, parity vectors extended.
- **D1**: new migration relaxing `scores_score_range` per §4.
- **Compatibility**: v1–v3 submissions, records, boards and stats are
  untouched; old clients keep working. Scores may now exceed 1,000,000 —
  every consumer that assumed the 1M cap (response schemas, DB CHECK, UI
  gauges) is updated or flagged.
- ADR-0028 and ADR-0029 are not deleted: they remain the contract for
  scoringVersion 1, 2 and 3.

## Verification obligations

- `baseScore ≤ 1,000,000` and `bonusScore ≤ 1,000,000` for every input,
  including boundary note counts (1, 49, 50, 51, catalog sizes) — contract
  tests on both sides.
- Perfect full-combo run = exactly 2,000,000; a no-miss clear always has
  `bonusScore = 1,000,000`; plays with misses get `bonusScore < 1,000,000`.
- Server accepts a legitimate v4 score > 1,000,000 (201) and rejects a v4
  score that disagrees with the recomputation (422); v1–v3 submissions
  claiming > 1,000,000 are still rejected.
- scoreKey separation: v4 local records use `@4` and never overwrite v1–v3.
- Parity: `contracts/parity/score-vectors.json` gains `scoreV4` /
  `scoreV4Settled` per case; Unity `ParityFixtureTests` and the Web
  `parity-score.test.ts` assert them **exactly** (integer math).
- Milestone bound checks apply identically to v4 submissions.
