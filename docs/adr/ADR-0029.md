# ADR-0029: Scoring v3 (combo milestone bonus and full-combo clear bonus) and scoringVersion 3

- Status: Accepted (amended 2026-11-18 by Issue #618 — see Amendment)
- Date: 2026-11-17
- Resolves: Issue #601; supersedes the v2 formula for new clients (ADR-0028 remains the contract for scoringVersion 1 and 2 records)
- Related: Issue #30 decision D5 (scoringVersion separation, confirmed by ADR-0028); Issue #618 (v3 regression fixes)

## Context

ADR-0028 introduced scoring v2 so that combo continuation and a no-miss clear
feed the score. Real-machine feedback on v0.1.29 (Issue #600) shows the v2
formula still lacks the game-feel the product asked for:

- No bonus is awarded *during* play at readable milestones, and the amount
  gained is not surfaced.
- A combo break ends all future bonus potential for that run; nothing lets a
  rebuilt combo earn again.
- A full-combo clear gets no dedicated end-of-song reward.

ADR-0028 explicitly rejected a sequential combo-history bonus because the
aggregate submission fields `(P, G, B, M, maxCombo)` cannot express it, so the
server could not recompute it. The product requirement now forces that
mechanic, so the contract must change: the path-dependent quantity is carried
by a new submission field that the server can **bound and price exactly**,
keeping the "server never trusts an unverifiable client claim" guarantee in
the same form ADR-0028 used for `maxCombo` (cross-check bound, then compute).

Code facts that constrain the design (verified against the implementation):

- `Combo` increments on every head hit outcome — Perfect, Great **and Bad** —
  and resets to 0 only on `ApplyMiss` (time expiry). `DowngradeHoldToBad`
  keeps the combo. HOLD notes count as one note and score at the head only.
- A settled chart satisfies `Perfect + Great + Bad + Miss == noteCount`.
- `maxCombo` is client-reported and only bound-checked (`<= noteCount`) — the
  established trust model this ADR extends.
- Catalog chart sizes (`Assets/Game/Resources/*.json`) range roughly 50–360
  notes; the tutorial chart has ~53.

## Decision

### 1. Scoring v3 formula

Constants (rationale in §1.1):

```
MILESTONE_INTERVAL = 50   // combo count step
MILESTONE_BONUS    = 25   // ratio points per milestone crossing
FULLCOMBO_BONUS    = 100  // ratio points, awarded once at song end
```

For a play of a chart with `noteCount` notes (N = P+G+B+M), `hits = P+G+B`:

```
judgment       = 5 * Perfect + 3 * Great + 1 * Bad        // unchanged
comboBonus     = maxCombo * 5                            // unchanged (v2)
noMissBonus    = (miss == 0) ? hits * 5 : 0              // unchanged (v2)
milestoneBonus = comboMilestones * 25                    // NEW (v3)
finalBonus     = judgmentsComplete && (miss == 0)
               ? 100 : 0                                 // NEW (v3)
// judgmentsComplete = (Perfect + Great + Bad + Miss == noteCount),
// i.e. every chart note has been judged — see §1.3
totalRatio     = judgment + comboBonus + noMissBonus
               + milestoneBonus + finalBonus
maxRatio       = 15 * N + floor(N / 50) * 25 + 100       // NEW (v3)
score          = round(1_000_000 * totalRatio / maxRatio) // cap kept
```

A perfect run reaches exactly 1,000,000.

#### 1.1 Why these numbers

The values are derived from the catalog's chart-size distribution and the
existing point scale, not from implementation convenience:

- **Interval 50**: with chart sizes ~50–360 notes, a clean run crosses 1–7
  milestones — frequent enough to give in-play feedback, sparse enough that
  each crossing reads as an achievement. Shorter intervals would fire too
  often to feel special; longer ones would rarely trigger on shorter charts.
- **25 points per milestone**: equals the judgment value of five Perfect
  notes (5 × 5). One milestone is therefore "five notes' worth" of score —
  noticeable but clearly below the per-note judgment stream. On a 300-note
  chart the milestone component caps at 6 × 25 = 150 ratio ≈ 10% of the
  judgment cap (5N = 1500): a meaningful secondary reward, never dominant.
- **100 points final bonus**: equals four milestone awards (20 Perfect
  judgments). It is flat rather than per-note so the "full-combo clear"
  reward is uniform and communicable across chart lengths; at N = 300 it is
  ≈ 22k score points, a visible climax without overwhelming the total.

#### 1.2 Milestone semantics

- During a combo run, each time `combo` reaches a multiple of 50 (50, 100,
  150, …), the client awards `MILESTONE_BONUS` ratio points once and shows
  the gained amount during play.
- Only `Miss` breaks the combo. After a break, progress toward the next
  multiple restarts at 0, previously awarded bonuses are kept, and later runs
  can cross milestones again — re-earning is intended.
- `comboMilestones` is the total count of crossings across all runs.

#### 1.3 Full-combo semantics

- `finalBonus` is awarded **once, when the play's judgments complete** —
  `Perfect + Great + Bad + Miss == noteCount` — if `miss == 0`. Under the
  settled invariant this is exactly "every note was hit", i.e. the combo
  never broke — the same condition `noMissBonus` already uses. Bad hits
  keep the combo and still count as a full combo, consistent with the v2
  premise that Bad is a hit, not a miss.
- "Judgments complete" is the same condition the song-end state machine
  uses to decide the play is finished, and it is the only completion state
  a submission can express (`perfect+great+bad+miss == noteCount` is
  enforced server-side). The bonus therefore vests when the last note's
  judgment settles — during the end sequence at the latest — and is never
  part of the live in-progress HUD projection (Issue #618).
- Distinctions the contract keeps explicit:
  - **完走 (completed)**: all notes judged, `miss == 0` → bonus vests.
  - **完走 with Miss**: all notes judged, `miss > 0` → no bonus.
  - **未完走 / 中断 (interrupted)**: notes still pending when play ends
    (deadline-forced completion, quit-to-result) → `judgmentsComplete`
    is false → no bonus; such a play cannot be submitted anyway because
    the judgment sum cannot equal `noteCount`.
  - **再試行 (retry)**: `GManager.ResetSession` clears every scoring
    field including the completion flag; a new attempt starts clean.
- The bonus appears in the result breakdown and is never awarded twice —
  it is a derived component of the settled aggregates, recomputed
  identically on every flush, not an incrementing counter.

### 2. Submission contract

`ScoreSubmission` gains one optional field:

```
comboMilestones: integer, minimum 0   // optional; omitted = 0
```

- The field is meaningful only for `scoringVersion = 3`. For versions 1 and 2
  the server ignores it (it cannot affect their formulas).
- For `scoringVersion = 3` the server verifies `comboMilestones` with the
  strongest checks the aggregate fields allow (Issue #618):
  - `maxCombo <= perfect + great + bad` — combo only grows on head hits,
    so it can never exceed the hit count (tighter than the v1/v2
    `<= noteCount` bound).
  - `miss == 0`: the whole play is one unbroken run, so the crossing count
    is **exactly** `floor(hits / 50)` — verified by equality. Over- and
    under-claims are both rejected.
  - `miss > 0`: at most `miss + 1` runs exist and each run is at most
    `maxCombo` long, so `comboMilestones <=
    min(floor(hits / 50), (miss + 1) * floor(maxCombo / 50))`. This is the
    tightest bound the totals allow; the exact crossing history (e.g.
    49 hits → Miss → 49 hits vs 50 → Miss → 48) cannot be reconstructed
    from `(P, G, B, M, maxCombo)` and remains a client-declared claim the
    server bound-checks but cannot disprove — the same trust model ADR-0028
    set for `maxCombo`. Violations are rejected with 422 like any other
    semantic diagnostic. The server then computes
    `milestoneBonus = comboMilestones * 25` itself; it never trusts a
    client-reported bonus amount.
- `scoringVersion = 3` is added to the accepted set; `LATEST_SCORING_VERSION`
  becomes 3. Omitted `scoringVersion` still means 1; versions 1 and 2 remain
  submittable and recomputable exactly as before.

### 3. Record separation

Unchanged rule from ADR-0028 — versions never overwrite or rank together —
extended to v3:

- **Local `ScoreKey`**: v3 records use `songId@chartVersion@3`; bare keys stay
  v1, `@2` keys stay v2.
- **D1 `scores`**: the existing `scoringVersion` column stores 3 for new
  submissions; no schema change is required (the column already exists).
- **Ranking / stats**: `scoringVersion` query parameter accepts 3;
  `stats` aggregates the latest version (now 3) only.
- **Result breakdown**: the client shows milestone bonus and final bonus as
  additional breakdown rows alongside the v2 components; these are display
  values computed by the same formula, not new submission fields.

## Alternatives considered and rejected

- **Keep v2 and add milestone bonus without a new field**: rejected — the
  server could not bound or price the bonus, breaking the recompute
  guarantee (the exact reason ADR-0028 rejected sequential bonuses).
- **Send per-milestone events (timestamps/counts per run)**: rejected —
  payload size and privacy/complexity for no verification gain; the count
  bound already caps the maximum claim.
- **Milestone bonus proportional to combo reached** (e.g. combo/10 points):
  rejected — less readable in play ("+X" varies per crossing) and harder to
  bound tightly; a flat per-crossing price keeps the contract simple.
- **Revise v2 in place (same scoringVersion=2, new formula)**: rejected —
  v2 records on devices and D1 would silently change meaning; a new version
  preserves the separation ADR-0028 established.
- **Final bonus scaled per note (`k * N`)**: rejected — flat 100 keeps the
  clear reward uniform and avoids re-tuning per chart; per-note scaling was
  already covered by `noMissBonus`.
- **Final bonus requiring all-Perfect (no Bad)**: rejected — would conflict
  with the established "Bad does not break combo" premise and punish
  borderline hits inconsistently with `noMissBonus`.

## Consequences

- **Unity** (#602): track per-run milestone progress in the judge path,
  award/display crossings live, apply `finalBonus` once at song end, extend
  `Scoring` with `BreakdownV3`, send `scoringVersion: 3` + `comboMilestones`,
  extend `ScoreKey` usage (already versioned) and the result breakdown.
- **Web** (#603): accept `comboMilestones`, bound-check and price it for v3,
  recompute v3 totals, keep v1/v2 paths unchanged, latest version = 3.
- **Contracts**: `contracts/openapi.v1.yaml` `ScoreSubmission` gains
  `comboMilestones`; `scoringVersion` description lists 3.
- **Compatibility**: v1/v2 submissions, records and boards are untouched;
  old clients keep working (omitted version = 1, v2 clients send 2).
- `score` stays within 0..1,000,000; the cap is unchanged.
- ADR-0028 is not deleted: it remains the contract for scoringVersion 1 and 2.
  Its "sequential combo-history bonus rejected" note is superseded for v3 by
  the bounded-field mechanism decided here.

## Verification obligations

- EditMode tests: milestone crossing, post-break re-earning, final bonus
  once-only and only after all notes settle (live HUD excludes it),
  interrupted/missed/retried plays get no final bonus, HOLD charts,
  boundary values, submission JSON carries `scoringVersion: 3` +
  `comboMilestones`.
- Web tests: v3 accept/reject (exact check when `miss == 0`, run bound
  when `miss > 0`, `maxCombo <= hits`), version separation on
  leaderboards/stats, v1/v2 regression.
- Cross-language parity fixtures (#612) must cover the v3 formula,
  including the `judgmentsComplete` vesting condition.
- Invariants: `0 ≤ score ≤ 1_000_000`, `comboMilestones ≤ floor(hits/50)`,
  `totalRatio ≤ maxRatio`, perfect run = exactly 1,000,000.
- Known model gap: with `miss > 0` the exact `comboMilestones` count is a
  client-declared value bounded by `(miss + 1) * floor(maxCombo / 50)` —
  a client can under-report (only hurting itself) or claim any count
  inside the bound, but cannot exceed it; with `miss == 0` the count is
  verified exactly. This is the accepted trust model, recorded here.

## Amendment (2026-11-18, Issue #618)

Post-merge review of PR #615–#617 found two contract violations, fixed
under Issue #618:

- **Final bonus timing**: `Scoring.BreakdownV3` awarded `finalBonus`
  whenever `miss == 0`, so `Judge.FlushScore` included the +100 in the
  live HUD score before the song ended. The formula now takes
  `judgmentsComplete` (`P+G+B+M == noteCount`, exposed as
  `GManager.judgmentsComplete`) and vests the bonus only then — matching
  the only completion condition a submission can express. §1.3 records
  the live-vs-settled distinction.
- **Milestone verification**: `comboMilestones <= floor(hits/50)` alone
  accepted claims that no run structure could produce (e.g. 49 hits →
  Miss → 49 hits claiming one crossing). §2 now requires equality when
  `miss == 0` and the `(miss + 1) * floor(maxCombo/50)` run bound when
  `miss > 0`, plus `maxCombo <= hits` for v3. The remaining gap — the
  exact count under misses is client-declared — is stated explicitly in
  §2 and the verification obligations instead of implying exact
  recomputation.

## Amendment (2026-11-19, Issue #631)

The original §1 wrote `score = round(1_000_000 * totalRatio / maxRatio)`
but both implementations actually used a **single-precision float** path:
Unity computed `ratioScore / maxScore` in `float` and the Web side
emulated it with `Math.fround`. The two environments do not guarantee
identical rounding (Editor Mono JIT vs IL2CPP vs Web), so a legitimate
play could submit a score one point away from the server's recomputation
and be rejected with 422 — the parity suite's ±1 tolerance documented the
drift instead of removing it.

Every v3 component is an integer (`totalRatio` and `maxRatio` are sums of
integer terms), so the division is exact rational arithmetic. v3 now uses
**deterministic integer floor division** on both sides:

```text
score = floor(totalRatio * 1_000_000 / maxRatio)   // exact, no floats
```

- Unity: `Scoring.ScoreV3` computes in `long` (`ratio * 1000000L / max`);
  `Judge.FlushScore` assigns that value directly instead of re-dividing
  floats.
- Web: `computeUnityScoreV3` does the same in IEEE-754 doubles — every
  intermediate is an exact integer below 2^53, so the result is identical
  on every platform by construction. Both parity suites assert the v3
  vectors **exactly** (no tolerance); only the legacy v1/v2 paths keep
  the float-emulation tolerance.
- The floor (not round) matches what the fielded float path already
  produced for every fixture case except two boundary values
  (`v1-mixed-139` / `v3-mixed-nomiss-139`: 957047 → 957046), which are
  re-pinned in `contracts/parity/score-vectors.json`.
- **Compatibility**: clients fielded before this change still submit the
  old float-derived value. The score endpoint accepts a v3 submission
  whose `score` equals *either* the deterministic recomputation or the
  legacy `Math.fround` result (`computeUnityScoreV3Legacy`), and always
  stores the deterministic value. v1/v2 submissions remain strict —
  their stored records and meanings are unchanged.
