# #394 画面外ノーツの Transform 更新削減 — 仮説だけ作り、実測で悪化が出たため取り下げ

## 1. 仮説と実装

- ノーツは 1 曲で最大 603 個 (Dogbite)。
- 既定 (`V6UiMode.Playfield = false`) の 3D 経路で、全ノーツが毎フレーム
  `transform.position` を書く。
- 画面に関係あるのは数十個なので、書き込みを省けば軽くなるはず、という仮説。

実装: `Notes.ShouldUpdateTransform(remaining)` で判定時刻までの残り秒を見て、
`+2.5 秒 〜 -1.0 秒` の外では Transform を書かない。判定は時刻表とキーで
行い Transform を読み返さないので、判定には影響しない (EditMode 6 件 + 全 1709 件 PASS)。

## 2. 実測結果 (正直な整理)

| 実行 | 起動方法 | load | median avgFps | メモ |
|---|---|---|---|---|
| before (`571bd357`) | 素の exec (無フォーカス) | 7.6→4.1 | 60.0 | 窓 3 つのみ・50 秒ちょっとしか取れていない |
| after (`5c801bd7`) | 素の exec | 4.7 | 8.0 | 窓 17 |
| after (`5c801bd7` 再試行) | 素の exec | 3.9→4.5 | 9.1 | 窓 16 |
| after (`f41c8fc3` revert) | 素の exec | 5.8→5.5 | 8.5 | 窓 17 |
| base | `open` 前面 | 4.8 | 8.8 | 窓 3 しか取れていない |
| A (`66baf651` のみ) | `open` 前面 | 6.5 | 9.0 | **A も遅い** |
| base | `open` 前面 | 6.5 | 58.8 | 窓 11、**60fps** |

いずれも 1 回ずつの実行であり、負荷帯・フォーカス・計測窓が統一できていない。

**この数字同士は比較にならない。** 素の exec 起動はフォーカスを持たず、
macOS が 8〜9fps にスロットルする。`open` で起動すると base は 58.8fps、
owner-review (66baf651) は 9.0fps、現行 HEAD は未計測 (比較不能)。

前提の訂正:

- 「baseline は 60fps、after は 8fps」という結論は **計測方法の混在** であり、
  変更の効果ではない。
- Control (detach-exec, 9.0) vs A (open, 9.0) vs base (open, 58.8) から、
  **フォーカスの有無** が最大の変数だったことが分かる。
- したがって「#394 の変更が性能を壊した」とも「直した」とも言えない。

## 3. 決定: 取り下げ

**効果の証明ができない変更を残さない。** 5c801bd7 はリバート済み (f41c8fc3)。
仮説 (画面外は書かない) は正しい方向だが、実機の描画パイプラインを考えると
Transform を書かないことでカメラ内に残るノーツが増える可能性があるため、
閾値を上げて計測し直す必要がある。

## 4. 次にやるなら

- `SetMeshVisible(false)` を Plan B として試す (判定線を過ぎたノーツを非表示に)。
- 測り方: `open` 経由で base 60fps・A 9fps・HEAD=? の順に並べ、負荷を記録する。
- メモリーか GPU 時間を Profiler で実測して、スループットだけでなく
  フレーム時間の分解を見る。

## 5. 注意 — 計測の信頼性

この調査は「前面に出ていない Unity は 8〜9fps になる」という事実を
**初めて意識した**ものであり、以後 `script/mac-fbperf.sh` は
`open -n <app> --args ...` で前面起動するように直してある。
これ以前の record はすべて計測環境が混在しているため、
**どの比較も再現条件が違う**。再計測はフォーカス条件を揃えてから行う。
