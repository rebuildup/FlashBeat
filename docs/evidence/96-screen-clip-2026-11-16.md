# #96 画面クリップ監査: 画面外に失われる情報・操作の実測 (2026-11-16)

## これは何の証拠か

`docs/evidence/96-241-resolution-matrix*.md` の行列は「指定解像度の画が
揃った」ことと機械チェック (フレーム収まり等) までを保証し、
**実画面の外に出る情報・操作の有無は未計測**だった。

本ディレクトリは `AutoTestV6Screens` に追加した画面クリップ監査
(`V6ScreenAudit.ClassifyScreenClip` / `AuditScreenClip`) の実測結果。
v6 Canvas 内の全 `Selectable` (押せる面) と `TMP_Text` のワールド矩形を
実画面矩形と照合し、`Inside` / `Partial` / `Outside` を
`autotest-v6screens-result.txt` の `[clip]` 行へ記録する
(**情報記録のみ。pass/fail にはしない**)。

## 実行方法

```sh
RESOLUTIONS="1024x768 1280x720 1920x1080 2560x1440 2560x1664" \
V6SCENES="TitleScene,SelectScene,OptionScene,ResultScene,GameScene" \
script/mac-resolution-matrix-v6screens.sh Builds/macOS/FlashBeat.app <出力先>
```

- Player: 本ブランチ (`w/96-reachability`) の macOS ビルド
- 各解像度 21 枚 (Title / Select 各種 / Option 4 タブ / Result / Result-RegisterModal /
  Game HUD / Pause / Loading)。証跡として result ファイルのみ収録
  (PNG は `Builds/res-v6clip-*` にあり gitignore 対象。画の実物は
  `96-241-resolution-matrix-v6-2026-11-16/` と同一画面のものが既存証跡にある)。

## 1024x768 / 1280x720 で画面外になるもの (実測)

固定フレーム契約 (1728x972 を 1:1、origin は中央寄せの負値) により、
フレームより小さい解像度では **Header (y 0-96) と Footer (y 876-972) の
ゾーン全体が画面外** になる。実測された主な喪失:

- **ポインタで押せない主操作** (Outside):
  - Select: `Op Ready` (決定/開始), `Button Settings`, Header の
    `Back` / `Search` / `Filter`
  - Result: `Op Retry` / `Op Register` / `Op OK` (フッター操作全滅)
  - Game Pause: `再開` / `リトライ` / `選曲へ` (フッター操作全滅)、
    `Tab Data`
  - Option / Select / History / Ranking / Title: Header の `Back` / `Exit`
  - History / Ranking: `この曲へ`、選曲クイック設定の `Prev`/`Next`
- **一部が切れる** (Partial): 曲リスト行 (左約 312px @1024x768)、
  Option の設定行、各種タブ、Pause のプレビュー/キー一覧。
- **見えなくなる情報**: Header の画面タイトル・曲情報・検索窓・
  ソート、Footer のキー凡例 (Space=決定 / ↑↓=選択 / Esc=戻る 等)、
  Result のスコアゲージ grade・判定内訳の一部、Pause のレーンラベル。

### キーボード経路は残る

画面遷移の主系はキーでも操作できる (Select: ↑↓/Enter、Result:
Confirm/Retry、Title: Enter/Space/Esc、Option: 矢印/Tab/Esc、
Pause: Esc でポーズ解除)。ただし **Header の検索・フィルタ、
フッター凡例、Result の判定数値の一部など、キーで代替できない
情報は視覚的に失われる**。ポインタ操作を前提にした導線
(マウスユーザー) は事実上使えない。

## 判定と残るオーナー判断

「1024x768〜で崩れなくする」を **現行契約 (スケールなし・
1728x972 固定フレーム・中央 origin) のまま満たすことは構造的に
不可能**。画面がフレームより小さい解像度では端が必ず切れる。

選択肢 (オーナー判断、T6「1024x768 profile 判断」):

1. **最小サポート解像度を引き上げる**: フレームが収まる
   1728x972 以上 (実用上 1920x1080 相当) を下限とし、
   #96 の対象解像度を再定義する。それ未満は「非サポート」
   として明記するか、起動時に警告/最小化を検討。
2. **小解像度用プロファイルを追加する**: 等比縮小または
   簡易レイアウトを Owner 承認のうえで実装する
   (「UI はスケールしない」Owner 指示の例外になるため要判断)。
3. **小解像度はキーボード操作のみを正式経路とする**:
   実装変更なしで #96 を「キー操作で全遷移可能・視覚欠落は
   既知の制約として文書化」として受け入れるかの判断。

Windows 実機での同等確認 (T5) と実ディスプレイでのフルスクリーン
受入は引き続き未実施。macOS の `-screen-width/-screen-height`
擬似解像度は実物理ディスプレイの代替ではない。
